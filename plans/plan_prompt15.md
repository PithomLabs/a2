## Goal

Implement Milestone 2 (Prompt 15) — payroll governance and reproducibility foundation — in dependency order P3 → P4 → P5 → P2 → P1 → P6, closing review findings SHG-B1a/B1b/B1c, SHG-B2a/B2b/B2c, C1, C2, C3, C4-STATUS, C6, and S5-F1, with zero statutory calculations and OT-001 left BLOCKED.

## Success Criteria

- One deterministic effective compensation basis per employee/classification/period; ambiguity blocks readiness and snapshot validation.
- SHG states (missing/pending/active-unverified/active-verified/verified-none/opt-out/superseded) are distinct, status-aware readiness emits machine-readable blockers, verified-none is service-recordable with evidence, and post-approval SHG changes conflict visibly.
- `app` cannot mutate `rule_pack_activation` or statutory parameter tables; activation happens only via a controlled admin CLI op with pinned identity/version/evidence, and is audited atomically.
- Every validated run owns exactly one immutable snapshot with a content-bound SHA-256 hash; drift invalidates rather than rewrites; concurrent population/comp/approval changes cannot produce mixed-version snapshots.
- Run lifecycle `draft → validated` enforced in service and DB trigger; `calculated`/`approved`/`finalized` unreachable without real artifacts that do not exist yet; no fake transitions.
- Full battery green: lint, build, `./...` under default/UTC/Singapore TZ, race packages, clean-server double run, `git diff --check`; `00001`–`00011` byte-identical; all work uncommitted.

## Approach

One new forward migration `00012` (all changes cohere: snapshot tables, SHG lifecycle, activation governance, run transitions — no second migration needed). Follow the M1.3 compensation precedent as the template for SHG governance (locking DEFINER functions, single-successor UNIQUE, live-basis overlap trigger, canonical in-function audit, app INSERT revoked → functions only) and for activation (narrow DEFINER function + revoked direct writes). Failing maintained test first for each behavior fix, real PostgreSQL 16 as `app`, persisted-state re-reads; disposable databases only.

Key decisions:

- **P3 resolver lives in `internal/compbasis`** (leaf package; `internal/hr` would create a test-only payroll↔hr import cycle) as `ResolveEffectiveCompensation(employer, employee, period)` returning per-classification an ordered, non-overlapping `[]EffectiveSegment`, each `{record ID, classification, effective interval, exact amount, terms ID, supersession lineage}` (Amendment C: one effective value per point in time, not one row per period); readiness and snapshot capture call it — no second implementation. Superseded predecessors excluded via the successor chain; multiple live rows covering the same date or broken chains return a machine-readable conflict, never summed, never `LIMIT 1`. For the first restricted profile, validation blocks any classification resolving to more than one segment in the period (mid-period-change treatment unimplemented).
- **P4 SHG mirrors compensation, not a new framework**: add `pending` (+ keep `active`/`verified_none`/`opt_out`) with a `verified` distinction carried by the existing `verified_at/by/basis` columns; `SetSHG` gains a verify path writing evidence+actor+date+provenance; new `correct_shg_instruction` successor function (one successor, original immutable, same-fund live-overlap rule); app UPDATE/DELETE revoked; `basis_seq` + `created_at` normalize triggers; post-approval conflict detector in readiness mirroring `checkTermConflict`. `opt_out` blocks until its semantics are explicitly defined (treated as `SHG_INSTRUCTION_INVALID`-family blocker); cross-fund multiples rejected as ambiguous for the first profile. New `SHG_*` blocker codes; readiness SHG check becomes status-aware.
- **Population barrier is an employer-level advisory lock** (`pay-population:<employer>`) taken by snapshot capture/validation first, then employee pay-basis locks in UUID-sorted order, then population revalidation — same convention joined by `CreateEmployee`, `SetTerms`, `SetStatus` (all already take the employee lock; they add the population lock first, preserving one global order: population → employee → pair/secondary). No new lock tables. Amendment A: capture runs at REPEATABLE READ (new `BeginSnapshotTx` helper) so all reads see one committed view; locks order capture against writers. Full lock set: population → employee (UUID-sorted) → per-required-pack activation key (`pay-pack:<employer>:<pack>`, also taken by the activation function) → revalidation. Direct-SQL population stability: BEFORE INSERT triggers on `employee`/`employment_terms` take the population lock (both are app-insertable; revoking would break onboarding); status already routes through `transition_employee_status`, which gains the population lock first. Reader tx cannot hit 40001; document why no retry loop is needed.
- **Snapshot schema**: `payroll_snapshot` header (run, schema version, hash) + `payroll_snapshot_employee` rows (term/status/sheet + line/interval IDs/comp-segment IDs + intervals/SHG record + evidence refs/per-employee `basis_seq`/inclusion decision + blockers) + run-level `snapshot_rule_pack` pins (pack, version, jurisdiction, interval, activation record ID, digest, evidence refs) (Amendment F). Canonical hash over stable-ordered JSON in Go (`crypto/sha256`, exact amount strings, sorted collections), excluding run/snapshot UUIDs and all timestamps so identical substantive inputs hash identically across runs. Amendment B: immutable content vs append-only `snapshot_lifecycle_event` (VALIDATED/INVALIDATED/SUPERSEDED + reason/actor); trigger enforces at most one VALIDATED-current snapshot per run; `payroll_run.active_snapshot_id` may reference only VALIDATED-current; freeze trigger + revoked app writes; revalidation inserts v(n+1) + SUPERSEDED on v(n), never rewrites.
- **P1 states**: extend CHECK to `draft/validated/calculated/approved/finalized`; DB transition-guard trigger enforces the edge graph (no draft→approved, no reopen, no finalize without approved artifact); `calculated`/`approved`/`finalized` additionally require rows in a `run_calculation` artifact table that has no writer in this milestone, making them structurally unreachable. Amendment D: `app` holds no INSERT/UPDATE/DELETE on `run_calculation` (SELECT retained), so direct SQL cannot fabricate artifacts; only `draft → validated` is reachable. Service exposes only Create/Validate/Inspect; exclusions stay draft-only.
- **P5 activation**: `rule_pack` registry (pack, jurisdiction, scope — identity only, never status) + `rule_pack_activation_history` (append-only, supersession-preserving) + `activate_rule_pack(...)` DEFINER function validating pack identity, exact version, dates, jurisdiction, scope, manifest digest, evidence refs, spec version, review record, verification status, actor, reason; app INSERT/UPDATE revoked on activation + all six param tables. Amendment E: the CLI-only admin command (privileged DSN, separate from `migrate`, documented as elevated, attribution not authentication) reads the on-disk manifest, asserts implementable lifecycle state, verifies referenced evidence/spec/review/fixture files exist, recomputes SHA-256 digests, and submits identity/version/digest/refs to the DB function, which rejects unknown packs, invented versions, and illegal transitions. No REST endpoint. Tests use temp-dir fixture packs, never `rules/`; real packs stay in actual states; OT-001 untouched.
