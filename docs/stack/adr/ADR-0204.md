# ADR-0204 — Provenance schema (immudb sidecar + PG back-links)

Status: PROPOSED (research gate; self-approved — no reviewer available, see §8).
Date: 2026-11-10. Revised Gate A (Z#1, ChatGPT#2); still PROPOSED, human approval required.

## Context

Snapshot hashes today are self-asserted REVOKE-less content (EF-E3, P0);
`audit_event` is a plain table — nothing external anchors `content_hash`/pins
(DOCUMENTED M2 §7; Phase 1 gap 2). D8 requires every validated/finalized run
reproducible from immutable inputs + pinned rule versions + approvals.
immudb v1.11.2 is BSL-1.1 source-available (DOCUMENTED Phase 4 §1; pin
VERIFIED via proxy 2026-11-10, tag time 2026-09-02, computed Change Date
~2030-09-02 — counsel to confirm); license decision is HUMAN-pending
(see DECISION-REQUESTS R1). Native Go SDK primary;
wire protocol rejected (binding Key Decision #6; reports PG14 + silently
skips DDL — DOCUMENTED Phase 4 §5).

## Decision

KV provenance records in standalone immudb via native Go SDK, hashes-only
(revised Gate A per Z#1 + ChatGPT#2):

- Key: `prov/{employer_id}/{artifact}/{artifact_uuid}/{event_uuid}` — every
  evidence event is a unique key; corrections form a chain via `supersedes`,
  never an overwrite (stable keys accept newer versions via ordinary Set).
- Value: canonical JSON `{event_uuid, artifact, artifact_uuid, pg_table,
  pg_id, employer_id, sha256, rule_pack, rule_pack_version, rule_pack_digest,
  calc_digest, decided_by, decided_at, supersedes}`. `immu_tx` is NOT in the
  payload (circular: the id is learned only after commit). `calc_digest` pins
  the calculator build so reruns detect implementation drift.
- Idempotency key `idem/{employer_id}/{action}/{uuid}` in the same `ExecAll`
  with `PreconditionKeyMustNotExist` (constructors DOCUMENTED
  `preconditions.go:19-48`); the marker VALUE binds event_uuid + content
  digest, so same-key-different-payload fails loudly on recovery instead of
  aliasing. `prov/...` and `idem/...` namespaces are never deleted or
  expired (`MustNotExist` treats deleted/expired entries as nonexistent).
- PG back-links: append-only `poc_ledger_backlink(pg_table, pg_id, immu_tx,
  alh, verified_at)`, insert-once (PK on artifact identity), inserted only
  after `VerifiedTxByID`. No UPDATE of provenance-bearing rows: the old
  nullable-column design is rejected (insert-only/freeze triggers forbid it).
- Trusted verifier state lives OUTSIDE the writing app (separate auditor
  host/volume); server runs with `--signingKey`; independent
  `immuclient audit-mode` auditor with `--audit-verify-values` + tamper webhook
  (DOCUMENTED primitives; placement INFERRED).
- Dual-write: PG txn (rows + outbox) → single-gated appender `ExecAll`
  (`noWait=false`) → `VerifiedTxByID` → PG back-link INSERT txn (INFERRED
  Phase 4 §4, reshaped Gate A).
- Artifacts recorded: content hashes/digests, rule-version stamps,
  decision/approval attestations, run-close records, KET receipts, outbox
  checkpoints, auditor root hashes. NEVER: PII, secrets, NRICs, bank details,
  primary entities, churn state (DOCUMENTED logical-delete limits
  `deleting.md:6`, `retention.md:14-20`).

## Alternatives considered

1. SQL-anchored provenance rows (`VerifyRow`) — DEFERRED: covers PK-anchored
   single rows only; full-row re-verification needs a prototype (DOCUMENTED
   Phase 4 UNRESOLVED 4). KV first.
2. Embedded immudb library — REJECTED: co-locates data+writer+verifier; no
   lock file (DOCUMENTED corruption risk); worse BSL optics (Phase 4 §2).
3. Wire-protocol integration — REJECTED (binding Key Decision #6).
4. PG-only provenance (hardened audit table) — REJECTED for tamper-evidence:
   no cryptographic anchoring; EF-E3 class survives (DOCUMENTED).

## Consequences

- Corrections = new immu tx + new PG row version + new backlink row, never
  edit (AGENTS.md §7 compatible; append-only at every layer).
- `ledger_tx` is canonical sequence, not PG commit order (INFERRED).
- Ops load: extra container, mTLS/auth, auditor scheduling, backup/restore,
  genesis pinning procedure (UNRESOLVED — first `GetState` bootstraps from
  server itself, DOCUMENTED `state_service.go:113-122`).

## Genesis procedure (Gate A; executed at first bring-up)

1. Start immudb with a signing key (`--signingKey`, key material in the
   auditor's custody, never in the writer's volume).
2. Run the auditor once with an EMPTY state dir and `--accept-genesis`: it
   verifies tx 0..N, persists state to its OWN volume, and prints the server
   UUID + genesis state hash.
3. Commit those two values out-of-band (git, signed) — this is the trust
   anchor. Every later run verifies continuity from the auditor's volume and
   refuses a server UUID mismatch (`ServerIdentityCheck`).
4. The writer's client NEVER shares the auditor's state dir (separate
   container/volume/creds per R2 model). Threat boundary: ledger operator /
   disk tampering. A hostile host admin holding both volumes is explicitly
   beyond the POC model (stated, not solved).

## Acceptance criteria (pinned before POC)

- [ ] Append → `VerifiedTxByID` → back-link round-trip green for run/pack/decision.
- [ ] Crash between ledger-append and back-link recovers with no dup/miss.
- [ ] On-disk ledger tamper → `ErrCorruptedData` + auditor webhook, PG truth intact.
- [ ] Ledger scan proves zero PII-bearing values (hashes/metadata only).
- [ ] Auditor re-derives snapshot hash from PG sources + pack, byte-equal.
- [ ] Genesis pinned out-of-band (procedure documented + executed).
- [ ] Same op_uuid twice yields one ledger event; same key + different payload fails loudly.
- [ ] `poc_ledger_backlink` has no UPDATE/DELETE path (trigger + revoke asserted).
- [ ] Every provenance value carries `rule_pack_digest` + `calc_digest`.
